Abstract—Students often turn long lecture notes into revision material with general-purpose chatbots, which may add facts the notes never taught and ignore length and format limits. This paper presents SmartStudy, a prompt-engineering system that converts lecture notes into a summary, key terms and practice questions with an answer key, where every term and answer carries a verbatim quote that program code verifies against the notes. We build six workflows (v0, a rule-based baseline; v1 to v5, LLM prompts of increasing structure: zero-shot, role with schema and evidence quotes, one few-shot example, a four-stage chain, and a length guard) and evaluate them live on Gemini 3.1 Flash-Lite with nine gold-labelled computer-science notes, eight automatic metrics and a 13-input test table of normal, edge and invalid cases. Structured prompting raised constraint compliance from 0 of 9 notes to 9 of 9 and answer support from 0.725 to 0.956; the final chain raised coverage to 0.676 with no ungrounded question, at three times the number of model calls. The test table passes 11 of 13 cases; both failures are the model padding thin or non-lecture input instead of warning. A post-hoc audit shows that every flagged invented term and most of the answer-support drop are measurement artifacts, and that key-term recall is capped because the model emits 3 to 6 terms against 10 to 36 gold terms. Code, prompts, data and a deployed prototype are released.
Index Terms—prompt engineering, large language models, lecture notes, study aids, grounding, prompt chaining, hallucination, educational technology.

I. INTRODUCTION

University students routinely face long lecture notes and little revision time. A common shortcut is to paste the notes into a general-purpose chatbot and ask for a summary and practice questions. This works only partly: language models can add fluent but unsupported content [1], summaries can be unfaithful to their source [2], and a one-line request rarely respects constraints such as the number of questions, a word limit or a mix of question types. For revision, a wrong answer key is worse than none, because the student cannot tell which items to trust.

This paper studies how prompt design, rather than model training, can make such a tool trustworthy. We present SmartStudy, a system that turns lecture notes into a short summary, key terms with definitions, and practice questions with an answer key. Its central idea is verifiable grounding: every key term and every answer must come with one exact quote from the notes, and ordinary program code, not another model call, checks that the quote exists. Where an exact check is possible, code does the work; where meaning is involved, the model does.

The contributions are:

  1. A four-prompt, two-guard workflow (v5) that combines prompt chaining, over-generate-and-filter, a quote guard, an independent moderator and a length guard (Section III).
  2. A controlled ablation of six workflow versions on a real hosted model (Gemini 3.1 Flash-Lite) with nine gold-labelled notes and eight automatic metrics (Sections IV and V).
  3. A 13-case test table with normal, edge (thin input, Hinglish, prompt injection, missing information) and invalid inputs; 11 pass and 2 fail, and both failures are analysed (Section V-F).
  4. A post-hoc validity audit showing which headline metrics mislead, including a recall ceiling set by the number of terms emitted (Section VI).
  5. An open implementation with a deployed prototype, 22 unit tests and no third-party dependencies.

Section II reviews related work, Section III describes the design, Section IV the method, Section V the results, Section VI discusses validity and engineering observations, and Section VII gives limitations, future work and the conclusion.

II. RELATED WORK

Prompting techniques. Few-shot prompting lets a model infer a task from examples in the prompt [3], and chain-of-thought prompting elicits intermediate reasoning [4]. Reynolds and McDonell frame prompt writing as programming in natural language [5]. Prompt chaining splits a task into steps whose outputs feed each other and makes each step inspectable [6]; SmartStudy applies this idea and assigns each step to either a model or code.

Verification and grounding. Retrieval-augmented generation grounds answers in retrieved passages [7]. SmartStudy needs no retrieval because the user's notes are the entire knowledge source; instead it requires the model to quote that source and checks the quote. Chain-of-verification has a model draft, plan checks and answer them independently to reduce hallucination [8], and strong models can act as judges of other outputs [9]. Our moderator follows the same independent-second-pass principle for questions. Faithfulness and hallucination in generation are surveyed in [2], [1].

Question generation and education. Neural question generation from text is an established task [10], and large language models offer both opportunities and risks for education, including incorrect content and over-reliance [11]. We therefore keep the output checkable by the student.

Prompt injection. Instructions hidden in input text can hijack a model [12], [13]. Lecture notes are untrusted input, so we include an injection case in the test table.

III. SYSTEM DESIGN

A. Requirements and Input/Output Contract

The input is the lecture text (40 to 20,000 characters locally, 6,000 on the public deployment), the number of questions N (default 5, clamped to 1 to 15) and a summary word limit (default 100, clamped to 30 to 300). The output is JSON with a summary, key terms (term, definition, evidence), questions (type, question, options, answer, evidence), a warnings list and a workflow trace. A pack meets the constraints when it has exactly N questions, a summary within the limit, at least three question types including a multiple-choice item, uses only knowledge in the notes, and every item has one exact, contiguous quote.

B. Task Decomposition and Final Workflow (v5)

Fig. 1 shows the final workflow. Four prompts (P1 to P4) call the model and three steps run as code. The allocation rule is simple: tasks with an exact answer (string matching, counting words, keeping the first N) are done by code, which is cheaper and more reliable; tasks that need meaning (topic outline, generation, answering from the notes, shortening) are done by the model.

  1. P1 Outline (LLM). Lists 4 to 10 topics with main points. This gives the next step a coverage checklist so no topic is skipped.
  2. P2 Generate (LLM). Returns the summary, key terms and N+2 candidate questions in a strict JSON schema, each with a verbatim quote.
  3. Quote guard (code). Keeps only terms and questions whose quote occurs in the notes (Eq. 1).
  4. P3 Moderator (LLM). A separate call sees only the notes and the candidate questions, answers each from the notes alone, and returns valid, a reason and, if the proposed answer was fixable, a corrected answer.
  5. Keep first N (code). Takes the first N survivors and never pads; if fewer remain it adds a warning.
  6. Length guard (code, then P4). Counts summary words; only if over the limit, P4 shortens it once, and a warning is added if it is still over.

D. Quote Guard

Let norm(·) lowercase text, map typographic quotes to ASCII and collapse every run of characters other than letters, digits and the apostrophe to one space. An item with evidence e is grounded in notes S when

grounded(e, S) = [ e ≠ ∅ ∧ norm(e) ⊆ norm(S) ](1)

where ⊆ is the substring relation. This makes the check tolerant of line breaks and punctuation but strict about wording. Note that it proves that the quote exists, not that the quote supports the claim.

E. Implementation and Deployment

The backend is Python 3.9+ using only the standard library: pipeline.py (workflows), llm.py (provider clients for Gemini, Anthropic and a local Ollama model), app.py (HTTP server and dashboard endpoints), evaluate.py (metrics) and m2_tests.py (test table); about 1,100 lines in all, plus a 696-line single-page frontend and 22 unit tests (all pass). The Gemini client retries HTTP 429 and 5xx replies after 2 s and 4 s, uses a 40 s per-call timeout, supports an optional fallback-model chain and records per-call timing. The same code runs locally and on Vercel through api/index.py; the API key lives only in environment variables or a git-ignored file. A record-and-replay provider lets the app run offline in a demo mode. The frontend offers Overview, Summary, Key terms, Questions, Quiz, Plan, Compare, Notes and Trace views and an evaluation dashboard that reads the result files. Fig. 2 shows a generated pack.

F. Robustness and Safety

The server validates and clamps all inputs, serves only a whitelist of project documents, binds to 127.0.0.1 when run locally and stores nothing. Model output is parsed leniently (code fences and surrounding prose are stripped); parse failures are returned in an errors list rather than raised. If the moderator reply cannot be parsed, the candidates are kept unverified and the error is recorded, so the quote guard remains the minimum protection. Notes are inserted into the prompt as data, and the system prompt forbids following instructions inside them; test 10 probes this.

B. Data Set and Gold Labels

The test set has nine original notes written by the team: six short (165 to 199 words; CPU scheduling, Big-O, normalization, TCP, gradient descent, prompting basics) and three long (528 to 1,037 words; memory management, model evaluation, software-engineering slides), 3,463 words in total. Each note has a gold file with key terms (10 to 36 per note, 173 in total, with accepted synonyms), must-cover idea groups (74 in total) and out-of-scope terms that are true but not taught, used to detect leakage of outside knowledge.

C. Model and Protocol

All LLM runs used Gemini 3.1 Flash-Lite [14], [15] through the Gemini API on 22 November 2026, with temperature 0.0, minimal thinking, N=5 questions and a 100-word limit, one run per version. Free-tier request quotas limited repetition. An earlier October experiment answered by a different model through helper agents was simulated, is stored separately and is not used for any claim here.

Thirteen inputs run through v5: seven normal (six notes plus a component test that sends a real 102-word summary to the length guard), four edge and two invalid. Structure fixes the format. Moving from v1 to v2 raised constraint compliance from 0 of 9 notes to 9 of 9 and answer support from 0.725 to 0.956. All 40 v1 questions were short-answer with no required mix and no quotes, so v1 could not meet the type rule by construction.

Recall follows list length, not quality. v1 has the highest term recall (0.358) because it lists about six terms per note (55 in total) against three in v2 (27), as the structured prompts never ask for a minimum number of terms. Section V-C shows this is a ceiling effect.

One example did not help (H2). Adding a worked example changed recall from 0.220 to 0.237 and lowered coverage from 0.622 to 0.568, and two questions carried a non-contiguous quote joined with “...”, which breaks the one-exact-quote rule. With one run per version, these small differences are not strong evidence.

The chain buys coverage and groundedness. v4 raised coverage from 0.568 (v3) to 0.676, a relative gain of 19%, and brought ungrounded questions from 0.044 to 0, at three times the calls. The quote guard removed one item in nine notes (a “Scrum” term). The moderator rejected none of the 63 candidate questions and edited the answer of 7 of the 45 kept ones, so on this data its measurable effect is small. Likewise the two extra candidates from N+2 over-generation were discarded unseen, because no question needed to be replaced.

The length guard never fired. Every summary was already at most 99 words, so v5 is identical to v4 on packs (H5 untestable there). The component test (test 7) shows P4 works: a real 102-word summary became 45 words against a limit of 60.

C. The Key-Term Recall Ceiling

v5 emitted 38 terms over nine notes against 173 gold terms. One-to-one matching would cap recall at 38/173 = 0.22, yet the reported recall is 0.254 (44 gold terms matched), so the lenient containment rule lets one output term match more than one gold entry. Recall therefore measures mostly how many terms the prompt asks for; it is an open weakness of the prompts and a loose scorer.

D. Cost and Quality

Fig. 6 shows that a threefold rise in calls (v3 to v4) bought about 11 coverage points. The 13-case test run used 34 calls, 30,153 input tokens and 19,054 output tokens: 11 v5 packs at three calls each plus one P4 call. The README's “about four” calls per pack is the worst case, not the typical one.

F. Failure Analysis

Both failures are the same behaviour. A 22-word, three-sentence note (test 8) and a 46-word Hinglish chat about the canteen and a cricket match (test 12) each produced five questions, two or three “key terms” and no warning. Every one of those questions was grounded, so the quote guard could not object, and the moderator only checks that a question is answerable from the text, not that the text is lecture content.

A likely cause lies in P2 itself: its output description says to produce “exactly the number asked” while a rule says to return fewer and warn when notes are thin. The model follows the stronger, repeated instruction. The prompt-injection case (test 10) and the missing-slide case (test 11) pass, and Hinglish (test 9) yields five terms and five grounded questions. Planned fixes are a code cap of N by note length, a lecture-content gate before P1 and removal of the contradiction in P2.

VI. DISCUSSION AND VALIDITY

A. Metric Audit

We audited the saved outputs and found that two headline numbers mislead.

Flagged terms are not hallucinations. Seven terms were flagged (five in v1, two in v4 and v5). Five are naming variants of terms the notes do teach: “Big-O Notation” (twice; notes say “Big-O”), “Learning Rate (alpha)”, “AUC-ROC” (notes teach “ROC curve” and “AUC” separately) and “CI/CD” (notes teach CI and continuous delivery). Two are acronym expansions, “Boyce-Codd Normal Form”, true but absent from the notes. So the true invented-concept count is zero in every version and the metric is a strict phrase check.

The answer-support dip is mostly a metric artifact. The scorer keeps only words longer than three characters, so a correct answer such as “UDP”, “O(n^2)” or “FIN and ACK” leaves no words and is counted unsupported. This accounts for 4 of the 6 unsupported v4 answers; the other 2 are paraphrases (overlap 0.33 and 0.57). v4 had more multiple-choice items (13 versus 9 for v3), which explains why its score fell from 0.956 to 0.867 without any outside knowledge being used.

C. Threats to Validity

Results come from one run, one model and nine computer-science notes written by the team that also wrote the gold labels, so differences of a few points are weak evidence. Term recall uses lenient matching and answer support is a word-overlap proxy. There is no human scoring yet. The test inputs 8 to 12 were designed to probe known risks, so failures there are informative rather than surprising. The authors kept losing versions and failures in the log.

VII. LIMITATIONS, FUTURE WORK AND CONCLUSION

A. Limitations and Future Work

  1. Padding. Cap N by note length in code, add a lecture-content check, make a warning mandatory for thin input and fix the P2 contradiction.
  2. Recall. Ask for every defined term with a minimum count, scale pack size with note length, and score with one-to-one fuzzy matching.
  3. Human evaluation. Two raters score faithfulness, coverage, question quality, summary clarity and usefulness on a 1 to 5 rubric.
  4. Stronger evidence. At least three runs per version with intervals, other models for comparison, more subjects and real student notes.
  5. Deeper grounding. Add a minimum quote length and a semantic support check (entailment) beyond substring matching; log latency and cost per pack.

B. Conclusion

SmartStudy shows that prompt structure and code-side checks, not a larger model, are what make generated study material verifiable. Role, schema and evidence quotes alone fixed format compliance and answer support; a chain with a quote guard added coverage and removed ungrounded questions at three times the cost. The study also shows what the automatic metrics hide: flagged terms were naming variants, the answer-support dip was a scoring artifact, and recall is capped by list length. The two remaining test failures, padding thin or non-lecture input, are the first items for the next milestone.

Reproducibility. Code, prompts and data are at the repository [16]; bash run.sh test runs the 22 tests and bash run.sh m2tests re-runs the test table with a Gemini key. A prototype is hosted at https://smartstudy-ai-swart.vercel.app.

P2 Study-pack generator (LLM)

===== SYSTEM PROMPT =====
You are an experienced teaching assistant who converts lecture notes into a revision pack for a university student. You use ONLY the supplied notes: never add facts, terms or examples from your own knowledge, even if they are true and relevant.

OUTPUT PARTS
1. summary: plain-language revision summary, within the stated word limit, covering every major topic in the notes.
2. key_terms: the important technical terms defined or explained in the notes. Each has a one-sentence definition written from the notes, and an "evidence" quote.
3. questions: the requested number of CANDIDATE practice questions with answers (a reviewer will filter them, so produce exactly the number asked). Mix the types: at least one "mcq" (4 options, exactly one correct, "answer" is the full text of the correct option), at least one "short" (answerable in 1-2 sentences) and at least one "true_false". Spread the questions across different topics rather than repeating one topic. Every question must be answerable from the notes alone.

RULES
- "evidence" must be ONE exact contiguous quote copied from the notes (no paraphrase, no ellipses) that supports the term definition or the answer.
- Do not write questions whose answer is not stated in the notes.
- If the notes are too thin to support the requested number of questions, return fewer and say so in "warnings".
- Output ONLY valid JSON, no markdown fences, no commentary.

P3 Question moderator (LLM)

===== SYSTEM PROMPT =====
You are a strict exam moderator. You are given lecture notes and candidate practice questions with proposed answers. For EACH question:
1. Answer it yourself using ONLY the notes.
2. Mark "valid": true only if the notes contain enough information to answer it, the proposed answer agrees with the notes, an mcq has exactly one correct option, and the question is clear and unambiguous.
3. If the answer is wrong but fixable from the notes, set valid true and give the corrected "answer". If it cannot be answered from the notes (outside knowledge), set valid false.
Output ONLY valid JSON, no fences:
{"reviews": [{"id": integer, "valid": boolean, "reason": string, "answer": string}]}
One review per id, in order.

===== USER PROMPT TEMPLATE =====
LECTURE NOTES
{notes}

CANDIDATE QUESTIONS
{candidates}

Return the JSON now.

===== SYSTEM PROMPT =====
You edit revision summaries. Rewrite the given summary so that it has AT MOST the stated number of words (count carefully; aim for about 10 percent under the limit).
